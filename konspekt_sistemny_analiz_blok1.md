# Системный анализ — Блок 1: основы требований

## 1. Виды требований

**Функциональные требования** — что система делает.
Пример: «Пользователь может отменить заказ, если статус ≠ "отгружен"».

**Нефункциональные требования (НФТ)** — как система это делает: производительность, доступность, безопасность, масштабируемость.

## 2. Три уровня фиксации требований

| Уровень | Что это | Пример |
|---|---|---|
| **User Story** | Короткая формулировка от лица пользователя, без деталей реализации | «Как клиент банка, я хочу видеть баланс счёта в приложении, чтобы не звонить в колл-центр» |
| **Use Case** | Разворачивает User Story в сценарий с шагами и альтернативами | см. структуру ниже |
| **ТЗ / спецификация** | Конкретные поля, форматы, коды ошибок, API-контракты (Swagger/OpenAPI) | «поле `balance`: number, currency: ISO 4217» |

## 3. Структура Use Case

- **Actor** — кто инициирует
- **Precondition** — что должно быть верно до начала
- **Основной сценарий** — шаги 1→2→3, чередование: актор действует → система отвечает
- **Альтернативные потоки** — что если что-то пошло не так (нумеруются `4.1`, `4.2` и т.д. — привязка к шагу основного сценария)
- **Postcondition** — результат

**Пример альтернативных потоков** (экран баланса, шаг «Система показывает баланс»):
- 4.1: сервис баланса недоступен → сообщение об ошибке + retry
- 4.2: данные устарели → показать последний известный баланс с меткой времени (это fallback-стратегия, trade-off между доступностью и актуальностью, а не ошибка)

## 4. Нефункциональные требования — рабочая формула

Чтобы НФТ было проверяемым, отвечает на 3 вопроса:

> **Что измеряем → где измеряем → для какого процента запросов/нагрузки**

Плохо: «Система должна быть быстрой».
Хорошо: «Время ответа API получения баланса — не более 2 секунд для 95% запросов (p95), измеряется на стороне сервера, без учёта сетевой задержки клиента».

Для доступности/отказов формула та же:
> «Если API не отвечает за 2 сек → одна повторная попытка → если повтор тоже таймаут/5xx → сервис считается недоступным → показать ошибку пользователю»

(На практике перед повтором ещё указывают задержку/backoff, чтобы не устраивать retry storm на перегруженный сервис.)

## 5. Конфликт требований от стейкхолдеров

Типичный вопрос на интервью: «расскажите, как разрешали конфликт требований».

**Алгоритм — не выбирать сторону сразу:**
1. Уточняющий вопрос каждой стороне: на чём основана позиция (риск / метрика), есть ли пространство для компромисса (например: «допустим ли доверенный период вместо жёсткой меры на каждое действие?»)
2. Перевести эмоциональные аргументы в измеримые (просить цифры, а не оценки типа «раздражает пользователей»)
3. Найти механизм, который закрывает реальный риск дешевле для UX

**Пример решения** (ИБ хочет re-auth на каждый показ баланса, продукт против):
> «Если пользователь прошёл аутентификацию не более N минут назад — баланс показывается без повторной аутентификации. По истечении N минут — требуется повторная аутентификация».
Параметр N — не техническая деталь, а результат согласования ИБ и продукта на основе оценки риска (фиксируется в ТЗ со ссылкой на согласование).

## 6. Sequence-диаграмма — минимум для старта

- Вертикальная линия = участник (актор, сервис, БД)
- Горизонтальная стрелка = вызов/сообщение
- Пунктирная стрелка обратно = ответ
- Читается сверху вниз — ось времени

**Управляющие блоки:**
- **alt** — взаимоисключающие ветки: «если A / иначе B»
- **opt** — одна необязательная ветка: «если условие выполнено» (частный случай alt, где вторая ветка пустая)
- **loop** — повторение действий

**Пример** (баланс с доверенным периодом):
```
Клиент → Auth-сервис: проверить доверенный период
Auth-сервис → Клиент: статус периода

alt период действителен
    (сразу к запросу баланса)
else период истёк
    Клиент → Auth-сервис: пройти аутентификацию (Face ID/пароль)
    Auth-сервис → Клиент: аутентификация успешна
end

Клиент → Balance-сервис: запросить баланс
Balance-сервис → Клиент: вернуть баланс
```
